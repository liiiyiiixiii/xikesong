# 红考拉自助烧烤 · Three.js 门店演示

本目录是当前 3D 前端；同级 `apps/web` 提供演示状态、事件和共享播放会话。3D 不生成业务重量、顾客或补菜任务。`legacy/` 保存旧版展示，不进入构建。

## 当前版本与来源

- 场景：`hongkaola-confirmed-65-180-v6`。本地权威清单是 `public/data/scene-manifest.v1.json`，主系统发布包必须具有相同摘要。
- 午高峰窗口：北京时间 12:00–12:10，共 600000 ms。
- 主轨：96 道菜、96 盘、47 席；备用轨：78 盘、33 席，默认停用。总计 174 盘、80 席。
- 当前数据包开场 31 人，新增 28 人、离店 12 人，窗口结束仍有 47 人；任务可以跨过观察截止时间。
- 菜品、客流、重量、任务和统计来自主系统的模拟数据包；尺寸、速度及容量为演示参数，未经门店实测。默认入口使用演示数据；`/?mode=live` 已通过独立适配器消费 v2 供餐业务接口，现场硬件真实性仍需单独验收。

完整版本与历史验收记录见 [SCENE-HANDOFF.md](docs/demo-v1/SCENE-HANDOFF.md)。其中 v5、24 顾客、约四分钟短片是历史版本；当前版本以文档开头的 v6 午高峰记录和磁盘数据包为准。

## 启动与页面

建议 Node 24。首次在仓库根目录执行 `npm ci`，再执行 `npm run data:extract`。依赖与共享契约由根工作区统一管理。已经运行的端口无需重复启动。

```sh
# 一个终端，在同级 red-koala 目录
npm run dev

# 另一个终端，在本目录
npm run dev
```

3D 开发入口是 <http://127.0.0.1:4173>，主系统默认在 <http://127.0.0.1:5173>。Vite 将 `/api/demo`、`/api/restaurant` 和 `/api/v2` 代理到主系统；默认配置使用 `/api/demo/v1`，业务模式使用同源 `/api/v2/session` 与 `/api/v2/serving/state`。

| 页面 | 功能 |
| --- | --- |
| `/` | 餐厅场景、俯视/立体/厨房近景、旋转缩放、餐盘详情、共享演示状态 |
| `/?mode=live` | 工作站登录、实际绑定固定排列、供餐余量/质量/位置依据、查找、业务工作台跳转 |
| `/menu.html` | 当前场景菜品目录、分类筛选和满盘模型预览 |
| `/plate-detail.html` | 固定中空托座与可拆卸金属碗/藤编盘的结构预览 |

三页都包含在生产构建中。`npm run build` 输出到 `dist/`，`npm run preview` 用于本地检查构建结果。静态服务器不会自动拥有 Vite 的代理：正式部署需配置 `/api/demo` 到主系统的路由，并更新 `public/data/config.json` 中的管理端/厨房端地址，避免保留本机地址。`dist/` 依赖 HTTP 服务，不能直接以 `file://` 打开。

## 数据与时间边界

`src/external-state.ts` 消费主系统 `lib/contracts/demo-v1.ts`。启动先校验本地场景摘要，再读取主系统 manifest/state；后续每 300 ms 读取快照并续接不透明事件游标。报告使用同一快照内的 reports，不再额外请求另一个时间点的报表。

所有视觉共用 900 ms 呈现缓冲；只允许向最新确认时间外推 250 ms，1500 ms 未收到状态时显示过期提示。暂停、完成、重播与重连会重新对齐时间。重复暂停/完成快照只保留一个有效边界，不随浏览器停留时间累积。快照及事件全部通过检查后才整体接受；冲突数据不会覆盖最后一次有效状态。

餐盘位置按共同 LUT 与 simTimeMs 推算，人物按主系统 movement 路径行走。断线不生成本地业务事件；场景不匹配时拒绝新数据，未连接时只显示布局。客户端不会暂停主系统的共享会话，其他页面仍可能继续播放。

## 场景维护

唯一几何源是 `src/demo/layout.ts`，`public/data/plate-bindings.v1.json` 显式保存盘位和菜品身份。承载位置、实际餐盘、菜品种类、有效座位、已入座、在店顾客与场景人物数量是不同口径。备用轨的物理座位不代表本次演示有人取菜。

`src/demo/dining.ts` 为渲染和占地检查提供同一套几何；路径按完整椅位、通道和入口连通性校验。室内陈设在 `src/interior.ts`，设备与工位定义在 `src/demo/interior-layout.ts`。

以下命令会改写场景文件，仅在确需调整布局或绑定时执行；一般检查无需运行：

```sh
npm run plates:fill
npm run scene:generate
```

布局或绑定发生变化后，必须协调主系统重新生成匹配的正式午高峰包。不要用旧版短片生成器覆盖当前 96 菜目录、绑定或摘要。

## 检查与验收

```sh
npm run typecheck
npm test
npm run build

# 可选：只在内存中运行主系统当前 generateRush 生成器
DEMO_PACKAGE_MODE=candidate npm test

# 可选：校验候选、磁盘包、HTTP 场景摘要，写本目录交接报告
npx tsx scripts/verify-seating-handoff.ts
```

默认测试直接读取主系统已发布数据包，严格检查场景摘要、身份、容量、动作窗口和全部动作边界前后 1 ms。完整几何与逐事件检查需要约数分钟。候选模式不写主系统数据，不代表运行中的 HTTP 服务已通过联调。

`npx tsx scripts/verify-live.ts` 是有副作用的完整 HTTP 验收：会暂停并重播共享演示，然后观察十分钟午高峰。只有需要重放验收时执行，其他页面的演示会同时受影响。本轮可靠性检查不要求运行它；历史验收不能代替当前真实设备联调。

## 供餐业务适配

参见 [EXTERNAL_DATA.md](EXTERNAL_DATA.md)。业务模式按真实 bindingId/scaleId/dishId 建立独立视觉实体，没有复用演示的 174 盘身份；未知余量和可信零分开，位置只显示后端区域依据，固定排列不表示实际运动。不生成顾客或员工轨迹。

本地隔离验证可设 `OPERATIONS_API_TARGET=http://127.0.0.1:5183`，只重定向 v2 代理。test/demo/live 标签来自会话与供餐服务且必须一致；环境名不是硬件验收结论。
