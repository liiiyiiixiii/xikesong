# 菜品时限管理与供应反馈

入口融入管理端原有“实时、每日总结、智能分析”三个栏目；旧地址 `/admin?view=freshness` 自动转到实时页，已有规则、批次和供应安排保留。厨房 `/kitchen` 仅在需要关注时显示紧凑提醒条，点击展开处理列表。

## 使用流程

1. 打开“设备与菜品设置”中的时限规则，选择菜品，填写门店确认的最长上台分钟数与提前提醒分钟数。没有预置食品安全时限，也不会用历史重量猜测上台时间。
2. 每个碗位分别登记新批次和实际时间；只允许补录过去24小时，且不能与上一批次重叠。开启规则后未登记的碗位显示“时间待核实”。初始重量不知道可以留空。
3. 补菜、页面刷新、设备重启或离线都不会重置截止时间。规则修改只影响新批次。正在计时的碗位不能换绑、校准、停用或关闭菜品规则。
4. 到时整盘取下，在“撤下 / 换新盘”中确认剩余重量、去向和原因。整盘取下后按设备稳定读数核实，匹配的减少量会在同一事务改记；部分撤下可匹配待确认事件或最近的取用事件，不结束批次，也不重置截止时间。可只撤下，或保存后立即上新盘。在线时核对设备已取盘与稳定余量；离线的人工登记保留，但反馈标为不完整。
5. 厨房页面开启提示音后，临近到时或到时提醒，每分钟重复；“知道了”只静音当前这组提醒，新的到时状态仍会响。需要保持厨房页面打开、浏览器允许声音；不是关闭浏览器后仍工作的系统推送。

## 数据与统计

`freshness_rules` 保存按菜品设置的规则；`freshness_batches` 保存每碗独立批次、截止时间和完成后的供应反馈；`freshness_decisions` 保存人工供应安排。每个碗位最多一个活动批次（数据库部分唯一索引）。管理端共享一份每5秒更新的提醒状态，客户端每秒检查时间状态。正常计时只在碗位详情中展示；卡片仅标记临近、到时和时间待核实，保留原尺寸和设备状态。“实时”旁的数量只统计已到时未处理的碗，点击可筛选。接口失败显示不可用，不显示为零。声音需主动开启，跨栏目及浏览器标签去重。

撤下、重量基准重置、报损/保留事件、反馈保存及可选新批次在同一个事务提交。设备版本控制与请求编号防止并发和重试重复报损。精确匹配的待确认减少量可在同一事务解决；不匹配时要求核实校正。原有“记录撤下”和“待确认重量变化”入口会打开兼容计时批次的同一处理表单，防止多个入口重复记录。新盘首次稳定称重作为补充量进入原有日统计；批次分析单独识别初始供给，避免再次计入批次补充量。

业务接口：
- `GET /api/freshness`：规则、计时、最近30天反馈、分时段建议及最近100条供应决策。
- `GET /api/freshness?mode=timers`：轻量轮询，不包含完成批次和决策明细。
- `GET /api/freshness?mode=feedback`：供应反馈，供单菜分析使用。
- `GET /api/freshness?date=YYYY-MM-DD`：北京时间当天撤下明细；支持 `startDate` / `endDate` 查询最多31天反馈。历史结果按截止时间过滤批次、重量事件与安排。
- `POST /api/freshness`：`rule`、`start`、`partial`、`close`、`decision`；批次操作必须显式确认，写入沿用现有同源校验。

新表有版本化迁移，也支持现有本地数据库的幂等初始化。维护期间不允许访问。冻结历史日期禁止补录批次；新的营业日允许用户明确确认的时限操作，不自动开启模拟或修改导入历史。

## 主体如何收到反馈

无需额外调用外部服务：厨房和管理端使用主体的同一个接口。完成批次就是持久化的反馈消息，与报损记录原子保存。主体提供三处使用入口：

- “智能分析”现有单菜展开详情内显示供应建议、批次依据与人工供应安排；历史周／日仅使用对应范围内的证据。
- “每日总结”原报损数值下显示“其中放置过久”，点击查看当日对应菜品的撤下记录。分项和总量来自相同重量事件；保留不计报损，没有批次的旧记录明确标注。
- `/api/preferences` 附带 `supplyFeedback`，备料计划按菜品显示运营提示与最新人工安排。保留模型的原始建议量，管理者确认调整。
- 智能分析增加只读 `freshness_feedback` 工具；普通分析和整体画像均可查询，返回真实日期范围、质量信息与人工决策。分析减供/停供问题时需结合已有取用统计。

所有建议和人工安排都不自动停用设备、下架菜品或改写备料量。厨房执行后，后续批次继续进入同一反馈列表；当前未实现自动因果评估或效果归因。

## 首版建议规则

按菜品编号及批次上台北京时间分组：早间0–11、午间11–14、下午14–17、晚间17–21、夜间21–24。撤下日期用于分析范围筛选。

可比较批次需在线核验、观测覆盖至少90%、初始供给已知、供给/取用/剩余近似守恒，无校正或待确认事件。缺失保留为缺失；反馈中的取用和补充标明“已观测”。

- 至少3个不同营业日、3个可比较批次在到时后剩余比例不低于30%，且这类批次占可比较批次至少50%，建议减少该时段单盘量、少量多次补充。
- 至少7个不同营业日、7个上述批次，占比至少70%，总体剩余比例至少70%，提示评估缩短供应时间或试停供。
- 其余继续观察；闭店撤下不算超时低需求证据，多个碗在同一天不算多个营业日。

这些是透明的首版运营规则，未经过预测准确率验证。没有客流，不能把超时直接解释成无人需要；不是自动取消菜品的规则。

## 验证

`npm test` 包含真实SQL语句在隔离内存SQLite的事务测试、原有称重回归和时限建议规则测试。测试不向现有门店库写入模拟批次。另执行 TypeScript、ESLint、生产构建，以及 `realtime-ui-smoke.mjs`、`daily-ui-smoke.mjs` 和 `freshness-ui-smoke.mjs` 浏览器回归。浏览器回归拦截业务接口并使用内存样本，不写入门店数据。仍需在实际联网秤和厨房浏览器上验证操作节奏与声音权限。
