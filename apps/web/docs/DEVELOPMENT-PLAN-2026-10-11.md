# 红考拉称重补菜系统软件开发方案

> 历史计划说明：本文保留设计阶段的起点与排期；其中“M0部分实现”等描述属于2026年10月11日。当前软件实现、结构图、验收对应和剩余现场条件见 [2026年10月12日运行与验收说明](software-delivery/OPERATIONS-RUNBOOK.md)。

编制日期：2026 年 10 月 11 日。状态：软件设计，M0 已部分实现、尚未完整验收。适用范围：当前单店项目的下一阶段开发。执行工期已改为 [六小时完整软件开发方案](software-delivery/SIX-HOUR-EXECUTION.md)，功能与验收范围保持不变。

本轮交付取用计量、供餐状态、补菜处理和经营统计四项能力。沿用当前项目，不重建技术栈。团队三人中，硬件同学负责设备实现；两名软件成员建议分别承担前端与后端，后端统一维护对外协议。本方案只规定软件接收什么数据、如何处理、如何验收，不涉及硬件选型、制造、安装或供电。

企业依据为《红考拉称重补菜系统需求记录》，会谈日期 2026 年 10 月 5 日。记录中的首阶段重点是可靠记录顾客取用和补菜提醒，尚未确认的规则不作为已承诺需求。本文的架构、接口、排期和测试目标是开发建议，不表示新增功能已上线。

## 1 交付范围和成功条件

| 范围 | 本轮交付 | 暂不交付 |
| --- | --- | --- |
| 取用计量 | 观测与业务分类分离、轮次核算、操作登记、质量标记、修正追溯 | 凭重量自动识别一切操作、精确夹取次数 |
| 员工工作 | 四档状态、补菜建议、前厅后厨处理、提醒与处理记录 | 自动调整排列、自动加盘或自动下架 |
| 经营统计 | 日、近十五天、近三十天、自然月的取用榜单和导出 | 收入利润、采购决策、多店汇总 |
| 既有能力 | 保留时限管理、撤菜报损、备料预测和分析入口，适配新口径 | 新建完整报损管理、跨日剩余全流程、个人画像和门口客流 |
| 对外接入 | 重量、设备状态、进出后厨事件协议及测试样例 | 设备本体实现 |

交付成功条件：一盘菜从出后厨、经过顾客区域、回后厨到形成取用记录可追溯；低余量触发的任务能由员工接手、处理和关闭；老板看到的统计与导出能够对账；证据不足时明确未知而非输出虚假确定值。

硬件尚未提供边界事件时，软件仍可完成接口、人工登记、模拟回放和操作流程。此时验收的是软件能力，不宣称自动轮次识别或真实取用精度已通过验收。

## 3 软件架构和职责

```text
重量与设备状态 ─┐
进出后厨事件 ──┼─ 接入校验与幂等 ─ 原始观测和事件
员工操作登记 ──┘                      │
                          绑定历史与轮次核算
                                     │
               ┌─────────────────────┴────────────────────┐
           实时余量估计                               正式计量账本
               │                                          │
        供餐状态与补菜规则                         日统计和区间报表
               │                                          │
          持久化补菜任务                            导出与只读分析
```

继续使用当前 TypeScript、React、现有框架运行层、Zod、Drizzle 和 SQLite／D1 接口。首版不引入消息队列或新的服务框架；后台重算和任务到期处理使用数据库作业表、租约及当前服务端调度机制，避免依赖单进程内存和浏览器常开。

新增模块建议为 `lib/contracts/operations-v2.ts`、`lib/operations/`、`lib/serving/`、`lib/refill/` 和 `lib/reports/`。共享类型和运行时 schema 由后端维护，前端使用同一契约。所有业务阈值、权限、任务动作和权威统计在服务端判定。

## 4 数据模型

下列名称为建议新增表。与现有 `scale_*`、`freshness_*` 和 `weight_*` 表通过 ID 关联，采用增量迁移。

| 实体 | 核心字段与约束 | 用途 |
| --- | --- | --- |
| `device_bindings` | id、scaleId、dishId、containerRef、validFrom、validTo、configSnapshot；同设备有效区间不得重叠 | 换盘、换菜、皮重与满盘标准的历史归属 |
| `device_events` | eventId、scaleId、bootId、eventSequence、occurredAt、receivedAt、type、payloadHash、sampleRef、origin | 边界、设备故障与迟到事件；同 ID 异内容冲突 |
| `weight_changes` | id、bindingId、fromSample、toSample、signedDeltaG、quality、algorithmVersion | 保存观测变化，不直接等同顾客行为 |
| `service_cycles` | id、bindingId、exitEventId、returnEventId、outG、inG、status、qualityReasons、revision | 每轮核算及不完整原因；同出区事件唯一 |
| `operation_records` | id、requestId、bindingId、occurredAt、recordedAt、type、weightG 可空、quantityStatus、actor、evidenceIds | 补菜、加冰、排水、撤菜、换盘、核实与更正 |
| `consumption_ledger` | id、cycleId、revision、weightG 可空、method、effectiveAt、recordedAt、supersedesId、evidenceIds | 每轮唯一有效版本；修订保留旧版本 |
| `serving_rules` | dishId、version、thresholds、hysteresis、halfPolicy、peakPeriods、enabled | 供餐状态和提醒规则版本 |
| `refill_tasks` | id、bindingId、status、priority、responsibility、assignee、deferUntil、version、verificationMethod | 每绑定最多一条活动补菜任务 |
| `task_actions` | requestId、taskId、beforeVersion、afterVersion、actor、action、at、payloadHash | 接手、交接、暂缓、完成、核验的审计与幂等 |
| `projection_jobs` | scope、desiredRevision、status、leaseUntil、attempts、lastError | 统计和分析缓存的可恢复更新 |
| `request_receipts` | callerScope、requestId、payloadHash、response、createdAt | 写操作重试返回同一结果，事务内保存 |

数据库唯一约束负责关键不变量：一设备同时只有一个绑定；一个边界只能开启一轮；一轮只有一个当前计量版本；一个绑定最多一条活动任务；一个请求只能产生一次业务影响。身份、状态、时间和版本等查询字段使用独立列，细节可继续用 JSON payload。

称重毛重继续为 `grossG`。必须分开表达承载净重 `loadNetG` 与食物余量 `foodRemainingG`；后者在冰、水等成分不可分离时为 null。旧 `netG` 的意义不得静默改变。换盘不要求硬件能识别盘号，可由软件创建新的绑定版本并记录人工来源。

## 5 取用计量规则

### 5.1 轮次边界和状态

`exit_kitchen` 表示餐盘离开后厨进入顾客区，`enter_kitchen` 表示餐盘从顾客区返回后厨。软件分配 `cycleId`，上报方不上传权威轮次号或取用量。

状态为 `open`、`pending`、`confirmed`、`invalidated`。同一绑定下的出口与其后入口配对；缺出口、连续出口、缺入口、绑定变化、边界顺序冲突均保留记录并进入待核实。拿盘、校准、重启或断线使当前轮次待核实，不自动用恢复前后差值补算。

边界优先关联报文中的 `sampleRef`。无引用时，软件在配置的时间窗口内查找可用样本；窗口大小属于运行参数，试点前需确定。只匹配没有跨越后厨操作的读数，歧义时不使用最近值强行确认。晚到的边界可以触发轮次重算，但不得倒退实时设备状态。

### 5.2 唯一正式口径

本轮新数据以完整顾客区轮次的质量平衡作为正式计量口径，连续差值只用于实时估计与核对。

```text
顾客取用候选量 = 出后厨承载净重 − 回后厨承载净重
                + 区内已知增加量 − 区内已知非顾客减少量
```

例如出后厨 800g，回后厨 600g，顾客区加冰 100g、排水 50g，则候选取用为 250g。此结果仅在容器和承重结构未变化、相关操作重量可信、没有未解释变化时才能确认。冰融化且水仍在同一承重结构内不单独记减重。

确认条件同时满足：绑定一致；边界配对可信；边界重量有效；期间无未解释缺测或拿盘；已知非顾客操作可核对；净结果在设定容差内合理；所有计算依据已保存。纯重量无法排除所有未登记操作，结果的业务可信度仍依赖现场登记约定，不能声称绝对识别。

负数、未知操作量和无法解释的变化转为待核实，不强行截为零。微小负数如落在约定计量容差内，可确认零并保存原差值和容差规则；容差必须由已配置规则明确给出。没有边界的连续下降只记旧口径观测或待核实，不转换为新口径已确认量。

正式轮次量与连续差值不得相加。旧数据用 `legacy_delta_v1` 标记；新轮次口径用 `cycle_balance_v2`。兼容旧界面时通过适配器读取账本，不向两套统计来源重复写同一取用。

### 5.3 时间归属与修订

保存事件发生时间、接收时间和修订时间。首版按回后厨时间归属轮次记账日期，跨午夜轮次标记 `crossDay`；报表注明“按轮次结束时间记账”，不宣称精确日内夹取时刻。首版日界为北京时间 00:00，营业日跨午夜规则若变更需版本化。

轮次量不按时间比例虚构分钟取用；分钟趋势可以展示已观测下降并标明估计。精确时段统计需要可信的区间证据；若只有边界量，只能按轮次结束时段归集并标明口径。跨边界查询显示相关限制。

补录及修正追加新版本，旧版本不删除。操作、账本修订、汇总版本提升和重算作业入队在一个事务中提交。报表返回 `projectionStatus` 与版本；重算中展示旧结果及标记，导出要求指定已完成版本或返回待更新，避免半更新数据。

日统计、区间报表、导出和 AI 证据使用同一账本版本。已保存画像保留当时版本，修正后标记过期并生成新版本，不悄悄修改历史分析；已有备料确认与执行记录保留，不因重算自动改动。

### 5.4 连续取用和余量显示

把采样过滤、实时显示和最终记账拆开。有效且新鲜的单次观测经过异常检查后可提供带质量标签的余量估计，稳定窗口用于更新确认值。持续下降时不能一直把旧确认值画成当前事实。

响应包含当前估计、最后确认值、各自时间及质量。供餐规则只在食物量可解释、数据足够新鲜时判定；持续取用可生成“疑似少量，请核实”的建议，不能将低可信估计标成确定空盘。设备不稳定超时生成数据核实提示。算法采用可解释过滤与回放验证，首版不依赖 AI 分类。

## 6 供餐状态与补菜规则

三个维度独立计算：`servingState` 为 full／half／low／empty／unknown；`recommendation` 为 none／watch／defer／refill／urgent／verify；`quality` 为 good／estimated／stale／offline／removed／unstable／pending。

四档需理解为业务标签：“半盘”是配置区间而非固定等于 50%。每菜设置空盘容差、少量上界、满盘下界及回滞；中间区间为半盘。校验阈值有序，进入和退出阈值不矛盾。配置缺失返回 unknown 与 `rule_not_configured`，不套用企业未认可默认值。

| 情况 | 供餐事实 | 建议及任务 |
| --- | --- | --- |
| 满盘且数据可信 | full | none，不建补菜任务 |
| 半盘，持续取用或处于配置高峰 | half | watch 或 refill，依据具体规则 |
| 半盘连续若干可信轮次变化小于阈值 | half | defer，保留实际状态和原因 |
| 少量且数据可信 | low | refill，生成或更新任务 |
| 空盘且数据可信 | empty | urgent，同一任务升级 |
| 离线、拿盘、食物余量未知 | unknown | verify，不冒充空盘，不自动关闭已有任务 |

半盘规则可配置连续轮数、变化阈值、观察时长及高峰时段；无真实轮次时不得拿浏览器动画圈数代替。按时间观察的降级规则需单独启用并标明口径。规则修改影响后续计算，历史事件保留当时版本。

阈值防抖采用回滞与持续时间。空盘紧急升级不能被长暂缓遮蔽；从估计状态升级时保留“需核实”。默认暂缓期限、重复提醒频率及升级时限均属于待确认经营参数。

## 7 补菜任务与员工操作

```text
open → claimed → verifying → resolved
  │        │          └ 核验失败 → claimed 或 open
  └────────┴→ deferred → 到期重新评估 → open
活动任务 → cancelled 仅限绑定结束或有依据的人工取消
```

任务按碗位绑定生成，记录触发原因、责任区域、接手者、创建和更新时间、操作历史、规则版本与允许动作。并发接手用任务版本进行条件更新；同版本只允许一个请求成功。一次缺菜过程只维护一个活动任务，少量变空只升级。

区域可信时，顾客区紧急任务提示前厅处理，后厨区域提示后厨；区域变化不静默替换已经接手的人，而是提出或记录交接。区域未知归为待分派。首版用工作站／班组身份区分厨房、前厅和管理端；若后续接入个人账号，再关联个人身份，不能信任自由填写的姓名作为认证。

“完成补菜”表示员工报告操作完成，任务先进入 verifying。只有匹配到补菜操作和可信余量恢复，或符合启用的人工核实策略，才关闭；单纯增重不能证明补菜，单纯点击也不代表设备核验。人工关闭需理由并保存 `verificationMethod=manual`。

加冰、排水、部分撤菜、整盘撤下和换盘共享操作服务。与现有时限批次相关的撤下必须复用原事务：处理重量、报损或保留、关闭旧批次、可选新批次和新绑定，不能调用多个独立接口重复记账。补菜不自动重置上台时限。

首版通知为页面内提示与可主动开启的提示音；任务生成、暂缓到期及升级由服务端运行。浏览器关闭后任务继续存在，但首版不承诺系统推送。前厅可复用工作台组件并按角色筛选，无需另建一套前端应用。

## 8 页面与交互

| 页面 | 首屏内容 | 主要操作与异常处理 |
| --- | --- | --- |
| 厨房工作台 | 紧急任务、待补菜、已接手、待核实，再列所有碗位 | 接手、暂缓、报告完成、交接；失败不提前显示成功 |

| 统计报表 | 日期范围、口径、确认取用、质量及排名 | 展开菜品和轮次，导出同版本数据 |
| 设置与接入诊断 | 菜品规则、绑定历史、最后采样／接收时间、接口错误 | 配置版本冲突提醒、设备状态排查 |

卡片显示实际状态、处理建议、质量和最后观测时间，重量与比例降为辅助信息。旋转展示可保留为排列视图，只有可信位置数据才能显示位置；首版不提供无依据的到达倒计时。

页面请求失败保留最后结果并明显标记过期；禁止回退到 mock 或空列表。轮询防止旧响应覆盖新响应。写请求使用稳定 requestId，重试复用；版本冲突刷新并提示处理结果。按钮按后端 `allowedActions` 展示，后端仍必须校验。

## 9 统计与分析口径

默认入口为今日、指定日期、近 15 天、近 30 天、自然月和自定义 1 至 31 天。最近 N 天包含所选结束日。自然半月是否增加由企业确认，页面不将近 15 天写成自然半月。

按菜品合并有效绑定的多碗记录，历史已停用菜仍应可在其经营日期报表查询，不因当前停用而丢失过去数据。按区间确认取用总量降序，重量相同按菜品编号稳定排序。零且有完整有效观测可排名；完全无有效数据不排名，不标成零。完整度不足但有确认量时排名注明“已确认部分量”。

字段包括确认取用、待核实轮数、旧口径观测量、有效观测覆盖、可信轮次覆盖、菜品缺菜分钟、经营天数及口径版本。没有足够证据不能给出“待核实取用克数”，只展示待核实变化及其性质。

观测覆盖按有效绑定应观测时长加权；轮次覆盖按可确认轮次／可核对轮次计算，边界丢失导致分母未知时返回 null。整道菜缺菜时间按当时应供碗位全部可信空盘的时间交集计算；一盘离线时无法证明整菜空盘。停供时间与空盘、离线分开标记。

总量与排名注明供应约束，不能等同顾客喜好、实际吃掉的量、营业收入或人数。CSV 与页面使用相同筛选、排序和结果版本；计量内部统一精度，建议采用整数毫克保存新账本、API 用克展示，汇总后再做显示舍入。

原有 AI 和预测在新旧口径混合时给出限制，不直接混合训练。旧模型继续读明确的旧口径历史，新模型只在有效的新口径样本满足既有门槛后启用。基础状态、任务、统计和导出不依赖模型服务可用。

## 10 接口与硬件交接

完整拟议契约见 [共同接口契约](software-delivery/INTERFACE.md)，对外清单见 [硬件对接清单](software-delivery/HARDWARE-HANDOFF.md)。现有重量上传保持路径和字段兼容，新业务接口使用独立版本路径。

M0 先完成 Zod schema、共享类型、正反样例和接口测试骨架，再冻结首版字段。设备只上传观测和事件，不上传顾客取用、满半空状态、任务优先级或经营推断。进出后厨能力可以单独对接；无自动事件时提供带人工来源的入口，不降低统计质量约束。

同 ID 同内容幂等成功，同 ID 异内容冲突；超时重试必须复用原 ID。接口回执逐项区分接收、重复、过旧、拒绝，接收只代表保存成功，不代表已形成可信取用。设备凭证、员工访问和管理配置权限分开处理。

## 11 迁移与运行

1. 核对当前未提交代码和数据库位置，保存一致备份，确定开发共同基线。本文不执行业务迁移。
2. 创建独立开发、演示和实际实例及凭证。实际实例不读取场景回放，不直接解除现有历史库冻结。
3. 增量建表与索引，旧记录不重写为新口径；绑定迁移从切换时点起生效，不能伪造过去的配置历史。
4. 按设备配置明确切换日期，先影子计算并对账，再切换读取。切换时结束或标记旧开放轮次，保留旧接口兼容。
5. 轮次账本生效后，旧连续取用不再作为同区间正式总量来源；采用服务端适配器过渡旧页面。
6. 原始样本保留期先保持现有 24 小时默认，并在试点实例显式配置所需诊断窗口；清理任务同时尊重待核实记录引用。已确认轮次永久保存边界重量、操作依据、算法版本和摘要，原始完整波形超期后不承诺全量重算。分钟保留 90 天，长期账本和汇总保留至确定归档规则。
7. 回滚优先关闭新入口和新计算，保留新表及新记录；实际写入后不能简单恢复旧库覆盖新业务。开发前提供备份恢复演练与故障恢复步骤。

接入和作业诊断至少包括上报延迟、重复和拒绝数量、待核实轮次、过期设备、失败重算作业、积压任务和最后调度时间。日志不包含凭证。后端作业至少实现重试、租约过期恢复及同一业务键去重。

## 12 开发任务和协作

沿用 [软件分工](software-delivery/README.md)、[前端任务书](software-delivery/FRONTEND.md) 和 [后端任务书](software-delivery/BACKEND.md) 的任务编号。采用一个 Codex 主集成和三个子任务并行，人员责任、文件归属、合并检查点及完整 360 分钟时间表以 [六小时执行方案](software-delivery/SIX-HOUR-EXECUTION.md) 为准。当前未提交与未跟踪文件必须进入共同基线，不能从旧 HEAD 创建工作区后忽略已有实现。

| 阶段 | 后端交付 | 前端交付 | 完成出口 |
| --- | --- | --- | --- |
| M0 契约与基线 | B01 schema、样例、错误码、数据迁移设计 | A01 页面结构、契约适配器及 mock | 关键正常／异常样例双方可运行，待定规则有明确配置位置 |
| M1 接入与计量 | B02 环境、诊断、边界接口；B03 绑定、轮次、操作、账本；B04 状态 | A02 实时与工作台；A03 操作及轮次详情 | 单盘完整流程可追溯；未知操作不冒充取用；连续取用显示不冻结 |
| M2 补菜处理 | B05 任务、并发、提醒调度和核验 | A04 任务处理；A05 配置与诊断 | 双浏览器协同，无重复任务、重复报损或错误关闭 |
| M3 报表和发布准备 | B06 报表；B07 回放、迁移、诊断和兼容验收 | A06 报表；A07 浏览器联调与使用说明 | 事件、页面、导出对账；异常恢复通过；交付包齐备 |

关键路径为 B01 → B02 → B03 → B04 → B05，报表 B06 在 B03 后可推进。前端契约 mock 完成后可提前建设任务与报表界面，但必须接入真实持久化接口后才能验收。

执行预算改为六小时实际经过时间，包含完整实现、集成、测试、修复和交付文档。M0—M3 继续作为能力分组与依赖，不再按人工工作日串行排期。软件范围与 T01—T16 不删减；完成状态由真实接口、持久化、页面和验收结果判定。

第 2 小时的单碗闭环是中途集成检查；第 4.5 小时前目标为全部功能接入，第 4.5 至 5.5 小时集中回归与修复，最后半小时核验最终产物并交付。真实硬件与现场验证独立记录，模拟回放不能冒充实机结果。

## 13 验收计划

测试真值只放在独立验证端；主体只接收实际上可得到的重量、边界和操作。历史导入已分类事件仍可验证报表，但不能替代识别链路验收。

| 编号 | 输入场景 | 必须验证的结果 |
| --- | --- | --- |
| T01 | 800g 出区、600g 回区，无其他变化 | 确认 200g，一轮一次，重复报文不变 |
| T02 | T01 加上区内加冰 100g、排水 50g，均有可信依据 | 确认 250g；加冰不计食物补充；未知重量版本必须待核实 |
| T03 | 后厨撤下 100g 后出区 | 后厨变化不算顾客取用；下一轮基线正确 |
| T04 | 每五秒减少 10g，无稳定平台 | 提供带时间和质量的实时估计，不把旧值冒充当前值；不凭动作数量统计夹取次数 |
| T05 | 半盘连续多轮未变化 | 状态仍半盘，建议可暂缓；缺轮时不虚构圈数 |
| T06 | 少量变空、暂缓中变空 | 同一任务升级；紧急情况不被暂缓隐藏 |
| T07 | 两人同时接手、超时重试、同 ID 异内容 | 仅一人成功；重试返回原结果；冲突不写入 |
| T08 | 员工报告完成但只检测到加冰 | 不自动确认补菜完成；核验依据可查 |
| T09 | 断线、恢复、拿盘、换盘、换菜 | 不补算未知取用；绑定和时限批次一致 |
| T10 | 边界先于关联样本、迟到入口、连续出口 | 能待关联或待核实；不错误配对，不倒退实时状态 |
| T11 | 同菜两盘，一盘空、另一盘有菜或离线 | 单盘任务正确；不错误宣布整道菜断供 |
| T12 | 跨午夜轮次、跨月查询 | 按轮次结束归属，跨日标记，查询与导出一致 |
| T13 | 撤菜更正过去已确认分类 | 原记录保留；汇总重算；旧画像过期；已有备料确认不被改写 |
| T14 | 无数据、可信零、部分覆盖、已停用菜 | null 和零区分；部分排名提示；历史菜品仍可查 |
| T15 | 浏览器关闭、服务重启、作业中断 | 任务保存；调度恢复；无重复记账 |
| T16 | 实际实例请求、回放数据、无权限写入 | 环境隔离、权限正确、没有静默 mock |

T01—T03 的重量是无噪声软件测试样例，不是实机精度指标。真实误差、允许漏报、端到端提醒时间和连续运行时长由团队与企业确定后补入验收配置。建议软件性能测试先以当前 42 碗位、每秒一条样本、三台操作浏览器为基准，分别记录接收耗时、处理耗时和页面延迟；若暂需工程目标，可采用 P95 接收响应小于 1 秒、已收到有效触发依据后页面更新小于 3 秒作为待验证目标，不能据此承诺动作发生后 3 秒提醒。

开发验证包括受影响的算法测试、真实 SQLite 事务与并发测试、隔离实例 HTTP 测试、TypeScript、lint、构建，以及双浏览器任务测试。保持原 126 项测试的业务不变量；因新口径变化调整期望时记录理由，不简单删除失败测试。

## 14 待确认事项与开发处理

| 事项 | 当前处理 | 影响出口 |
| --- | --- | --- |
| 四档阈值及半盘规则 | 配置机制先开发；演示参数仅在测试 fixture 中 | 正式开启自动提醒前确认 |
| 半月含义 | 先明确显示近 15 天；自然半月单独选择 | 报表验收 |
| 进出后厨事件可用性 | 自动接口和人工入口都实现，来源分开 | 自动轮次计量验收 |
| 边界读数窗口与时钟误差 | 运行参数与异常分支先实现 | 联调验收 |
| 前厅后厨分工及人工关闭权限 | 角色与任务能力可配置，不预填真实人员 | 现场流程验收 |
| 加冰排水等登记是否可执行 | 支持已知／未知重量和待核实，不假设员工每次都能测量 | 取用可信度验收 |
| 精度、延迟和稳定运行目标 | 测试输出测量结果，未定目标不标通过 | 最终验收 |

这些待确认项不阻止契约、数据模型、基础页面和异常处理开发；未满足对应条件的能力不得包装成已完成现场验收。
