# 红考拉称重补菜系统需求记录

本记录依据 2026 年 10 月 5 日门店会谈转写整理，供项目团队和 FDE 梳理后续开发。第一阶段重点是可靠记录旋转线上的顾客取用量，并给员工提供供餐状态和补菜提醒。减少浪费是业务目标，菜单、排列和供应链决策由企业产研及运营负责。

来源为用户提供的《旋转自助烤肉门店智能称重补菜系统需求沟通与方案探讨》Markdown 转写。文件第 270 行起重复前文，本记录按一次会谈处理，略去广播与闲聊。转写未明确标注发言人，角色归属依据上下文判断；本文不是双方确认的需求规格。以下行号对应原文件。

## 现场流程与提醒规则

后厨完成补充或其他处理后，餐盘出后厨进入顾客区域，随后返回后厨。会谈讨论以“出后厨”和“回后厨”的重量作为一轮统计边界，减少后厨加菜、加冰等操作对顾客取用量的影响。第 125—143 行。该方法是候选方案，识别边界、绑定餐盘及处理期间变化的具体机制未确定。

| 状态 | 按后续反复陈述整理的操作规则 | 尚需确认 |
| --- | --- | --- |
| 满盘 | 通常无需补充。 | 各菜标准满盘重量、皮重与阈值。 |
| 半盘 | 员工结合经验判断；高峰或持续取用时更需关注，连续多圈未变化可暂缓。 | 转写同时出现“必须补”与“可补可不补”，需确认最终规则；圈数与时间门槛未定。 |
| 少量 | 应补充。 | 提醒提前量、责任人及具体阈值。 |
| 空盘 | 紧急处理；在前厅时前厅人员参与，返回后厨时后厨处理。 | 餐盘位置判断、通知方式及任务交接。 |

开发建议：分别保存实际供餐状态与补菜建议。“半盘但暂缓补充”应保留半盘事实，不能为抑制提醒把真实状态改成满盘。离线、拿走餐盘和读数异常也应单独表达，不能归为空盘。

现场提到“进去到出来约 40 秒”，但未明确两端位置，也未证明是完整一圈的时间。不能直接将其设定为循环周期。转速被描述为基本固定，仍需现场测量和确认。

## 当前讨论的硬件与数据方案

团队提出在各餐盘或承载位置下安装称重装置，使用压敏电阻，经过采集和联网后向后端发送数据，厨房页面显示状态与提醒。餐盘与承载位置是否一一固定、设备编号如何绑定菜品、供电和通信方式均待确认。

会谈中的以下内容属于估计或设想：

- 每 3—5 秒刷新一次数据：属于讨论目标，未形成端到端实测结果。
- 单个装置约 10 元、量产可能更低：属于团队估计，是否包含采集、通信、供电、外壳、装配、安装及维护尚不清楚。不能按菜品数直接替代硬件点位数。
- “量程正负 100—200 克”：转写含义不清，可能混用了量程、误差或变化幅度，需核对实际器件规格。
- 防水防油外壳、温度影响较小及故障更换方便：属于讨论方案，需安装后的实测依据。

菜品会加冰，部分位置有蜡烛加热。这是老板明确提出的现场干扰。仅有重量信号时，相同增重可以来自补菜或加冰，需要操作记录或其他观测才能区分；不能将“AI 会识别”视为已验证能力。冰融化后仍留在同一承重结构内时，总质量不因相变而减少；排水、泄漏或蜡烛燃烧等造成的变化需要独立考虑。上述为分析与验证建议。

即使首版不交付报损报表，开发仍需考虑员工撤菜、排水等事件怎样避免误计为顾客取用。重设出后厨基线有助于排除此前的后厨操作，但不能自动解释顾客区域内所有重量变化。

## 开发阶段与演示约定

会谈先将可靠采集和呈现顾客消耗称为 P1，将辅助看线人员安排后续工作、提升人效称为 P2，更复杂的模型和经营优化作为后续方向。后半段又讨论门口客流，这是一条可另行评估的方向，不能与前面的阶段标签直接等同。

初步可演示原型被讨论为“一个礼拜内”。同时出现“8 日到 15 日”和“从今天往后算”，因此准确交付日期及是否包含真实硬件联调需要确认。转写没有形成关于精度、稳定运行时长、提醒延迟或经营改善幅度的正式验收指标。

建议首版演示按三条流程组织：餐盘识别与数据接收；顾客区域的取用统计；四种供餐状态与员工补菜处理。该组织方式是建议，不是已确认交付承诺。

## 测试数据需要补充的场景

以下为基于会谈提出的测试建议，供负责合成数据的成员与开发者共同确认预期结果。

| 场景 | 核对重点 |
| --- | --- |
| 后厨补菜后出盘再回盘 | 正确建立每轮基线，统计顾客区域变化，避免重复累计。 |
| 加冰、排水、换蜡烛及加热 | 区分食物变化与非食物重量变化；无法识别时保留不确定性。 |
| 同一采样间隔内多次取用 | 总重量变化与动作次数分开评估，避免声称精确夹取次数。 |
| 整盘拿走、换盘及换菜 | 重新建立基线，维护设备与菜品绑定，避免虚假取用。 |
| 半盘连续多圈未变化 | 暂缓提醒，同时保留真实半盘状态。 |
| 高峰快速变少或变空 | 及时提醒，验证前厅与后厨的接力处理。 |
| 设备断线及恢复 | 缺测不等于零余量，恢复差值不自动补算为顾客取用。 |
| 重复报文及乱序报文 | 不重复记账，不用旧数据覆盖最新状态。 |
| 长时间缺菜 | 排名注明供应约束，不能把低取用直接解释为低喜好。 |

合成数据应分别保存模拟真值、系统可获得的观测和预期处理结果。数据通过程序校验库存与事件一致性；模拟真值仅用于外部核对，不能提前泄露给系统作为已知输入。

## 下一步需要确认的信息

1. 首版是否包含报损记录、明日备料预测或门口客流，还是先集中做取用统计与补菜提醒。
2. 实际菜品数、餐盘或秤点位数、固定排列、换盘换菜流程，以及一个菜品是否对应多个盘。
3. 传感器型号、总量程、变化分辨能力、稳定误差、采样频率、供电通信和完整成本。
4. 后厨入口与出口的位置、真实循环周期，以及如何判断餐盘所在区域和轮次。
5. 各菜满盘标准、四种状态阈值、半盘提醒逻辑和前厅后厨的责任分配。
6. 顾客取用、非食物变化和员工操作分别怎样记录；夹取次数是否仅作估计。
7. 演示日期、硬件接入范围、验收指标及试点门店负责人。

这些问题需要团队与企业进一步确认，会谈中的探索方案仍需经过现场验证后才能形成最终规格。
