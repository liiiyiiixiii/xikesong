## 计量设计约束

保留原始样本和接收时间，独立保存重量变化、操作、轮次和分类依据。业务分类记录需包含引用的原始依据、规则版本及修正历史。原始记录保存周期做成运行配置；试点需要回查的时间窗口不得被清理脚本提前删除。

轮次由同一有效绑定期间的出后厨、回后厨事件配对。软件产生 `cycleId`；边界重量从附近有效观测中关联，容许时间窗口由可配置规则确定。边界重复、延迟到达、漏报、时间倒退或绑定变化时进入明确的质量状态，不强行凑成完整轮次。

在边界与相关操作都可信时，区域内质量平衡为：取用候选量等于出区重量加区内增加量，减回区重量，再减区内非顾客减少量。冰、水及其他非食物变化必须有可用依据；无法分离时标记待核实。负结果、未知操作量或异常大差额不能静默截断为零并标为可信。

连续重量变化可用于实时估计，轮次用于核算；正式记账只能有一个权威口径，不能把两者相加。引入新口径时为旧数据标记计算方式，不把历史自动分类无条件升级成已确认取用。

持续下降无稳定平台时，允许输出带质量标记的实时估计和最后确认值，但不能把估计直接改称确认。记录最后观测时间及最后确认时间，页面才能识别旧值。状态持续不稳定的超时处置也应明确。

操作登记应区分“操作确实发生”“操作重量未知”“操作已匹配观测”。员工填入一个数值不代表系统已验证。加冰后食物余量不能直接等于总净重；非食物剩余量无法确定时供餐状态可为未知。

换盘、换菜、校准、重启和断线恢复可能要求建立新基线。绑定历史应有生效区间，历史事件归属按事件发生时绑定确定。现有活动时限批次的限制不能绕过。

## 状态和任务设计约束

服务端独立返回供餐状态、补菜建议和数据质量，规则按菜配置并保存版本。四档边界、回滞区间、高峰时段、半盘连续轮次及暂缓时长均需可配置或明确未配置；前端不计算这些规则。

同一碗位的缺菜处理保持一条活动任务，状态或紧急程度变化更新该任务。规则计算和任务写入通过数据库约束及事务去重；不能仅依靠单进程内存锁。

任务状态建议为 `open → claimed → verifying → resolved`，另有 `deferred` 和 `cancelled`。暂缓到期重新评估；优先级升级仍保留同一任务。质量不足时保持待核实，不能凭设备离线自动关闭。

员工点击完成后记录操作，按可用称重或明确人工核实策略关闭任务，并保存 `verificationMethod`。人工核实不能标成设备核验。交接更新责任区域和处理记录，避免两组员工重复执行。

所有人工写操作使用请求编号；同号同内容返回原结果，同号异内容返回冲突。任务与配置使用版本号进行并发检查。任务、事件及其对统计的影响需要原子性；失败不允许只写一半。

操作者身份如已有可信登录会话，从服务端会话获得；不能相信任意客户端传来的姓名。首版若没有员工账号体系，可记录工作站或班组来源，并明确它不代表已认证的个人身份。接口访问控制与前后厨任务责任是不同概念。

## 统计和运行要求

取用总量、排名和导出由同一服务端查询逻辑生成。分别返回旧口径观测量、新口径确认量和待核实记录；不明减少不都认作潜在顾客取用。跨口径数据禁止无提示相加。

同一道菜多个碗位按菜品汇总；整道菜缺菜时间按所有有效碗位同时空盘的交集计算，不能累加各盘空盘时间。历史数据不足以确定交集时返回未知或明确有限口径。

修正事件后更新受影响日期的汇总与版本，使页面、导出和分析缓存失效或重算。缺失值保留为 `null`；真实零和未知需要区分。基础统计不调用大模型。

调度任务应在服务端运行，不依赖厨房页面常开。实际和演示实例使用独立库与凭证；通过配置选择环境，不用解除历史冻结来混入真实数据。为数据库迁移提供备份、失败恢复和兼容旧数据的说明。

## 测试和对外交付

保留既有称重测试，增加真实 SQLite 事务、并发写入、幂等冲突、任务状态转换、轮次配对和分类修正测试。接口测试使用隔离实例，不写现有经营数据库。

回放必须把模拟真值留在验证端，只向正式 HTTP 接口提供系统实际能获得的读数和事件。历史导入的已分类事件可验证汇总，不能代替从读数识别的验收。增加持续下降、操作量未知、迟到边界和跨日轮次用例。

交付给 A：契约提交版本、运行方式、接口样例、种子场景、错误及冲突示例、迁移说明、测试结果。交付硬件同学：接口地址占位表、凭证发放方式、合法报文、重试规则、异常回执和联调步骤。
