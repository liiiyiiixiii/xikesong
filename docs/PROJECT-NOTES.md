## 3. 当前代码体现的重点

### 厨房端的信息聚焦

厨房端突出工作人员最需要的信息：**补什么菜、补多少、最近一盘何时到达补餐口**。待补菜品按预计到口先后排列，任务汇总和历史记录保留在管理端。

到口倒计时与补菜截止时间独立。真实模式依赖设备上报 `refillArrivalAt`；预测缺失、异常或过期时显示待接入或待更新。模拟模式使用明确标注的 3 分钟转盘周期。

### 识别与称重数据的业务处理

已建立 `/api/ingest` 采集接口，接收盘子生命周期标识、菜品、净重、件数、可信度及撤盘事件，支持设备令牌认证、事件去重和批次原子提交。

同一盘跨圈观测不会重复计入库存；重量下降用于估算取用，重量增加用于推定同盘补充。低可信度、超容量、件数与重量方向矛盾、过期读数等情况会暂停相关自动派单。

**当前应用主要处理上游识别和称重结果，真实视觉识别、称重硬件及采集链路仍待接入。**

### DeepSeek 分析助手

已实现经营问答入口，以及页面内 API Key 验证、保存、测试、更换和移除流程。密钥在服务端加密保存，页面仅显示遮罩。

未配置模型时使用明确标记的规则分析；配置后调用 DeepSeek，失败时显示错误。模型负责分析与建议，自动补菜由确定性规则执行。项目文档注明：真实 DeepSeek 调用尚未联调。

### 数据持久化与模拟隔离

模拟数据与真实数据分别保存到 D1 数据库，共用业务流程但保持来源隔离。真实模式初始没有虚构订单和报损历史，默认关闭自动派单，菜品参数需现场确认后用于自动补菜。
