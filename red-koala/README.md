# 红考拉：餐饮数据处理与智能经营分析系统

项目采用两层架构：第一层整理外部接口数据并计算可靠的经营指标，第二层由 LLM Agent 调用查询、统计与预测工具，形成客群取用行为分析、供应建议和管理层经营洞察。默认先服务当前单店。

当前已实现数据处理、实时与每日统计、菜品取用趋势及明日备料预测，并接入智能分析首版。管理端的“智能分析”支持 DeepSeek 工具调用、日统计与时段观测分析、只读备料试算、证据核对及报告导出；需要配置服务端模型密钥。厨房端继续服务现场供菜，完整客群分层与经营实验仍待建设。

首阶段不建设个人画像，不把取用重量直接等同于喜爱程度；没有客流数据不计算人均指标，缺少完整成本收入不输出完整利润结论。未来排列与供应实验需区分相关性和因果影响，供应调整由管理者确认。能力路线、数据依赖和结果规范见 [两层架构与分析设计](docs/ARCHITECTURE.md)。

## 智能分析入口

访问 `/admin?view=intelligence` 或点击管理端“智能分析”，首页显示一张紧凑自然周卡片，通过上一周／下一周切换，点击进入整周／每日可视化画像；图表无需模型密钥，已连接模型时自动生成综合解读。全部菜品只使用一张可展开明细表，每日、时段及四周依据在行内呈现。提问是折叠辅助功能。页面最下方填写 DeepSeek API Key，测试成功后加密保存即可接入；也兼容原有服务端环境变量。未配置或调用失败会明确提示，不生成替代分析。详见 [配置、工具与验证说明](docs/INTELLIGENCE.md)。

## 当前运行形态

每个碗下方安装联网秤，通过主设备每秒上报重量。界面只分管理端和厨房端，所有数量以克存储、以克或千克显示。

## 本地运行

要求 Node.js 24。已有本地数据库时：

```sh
npm ci
npm run dev
```

访问 http://127.0.0.1:5173/ 。`/admin` 管理实时余量和每日总结；`/kitchen` 将所有菜品排在首尾相连的闭合环路上，补菜节点位于下方放大区域右侧。最近的 10 道菜在下方分两行、每行 5 道，占据约半屏，其余保持普通大小，卡片显示菜名、剩余百分数及余量条。界面不显示中心说明文字。数据每秒更新，转盘每五秒前移一道菜，沿环路移动并平滑缩放，支持暂停和减少动画。

在管理端的设备设置中填写秤编号、菜品、碗皮重和标准满量，再生成设备凭证。百分数始终以设置的标准满量为基准。凭证只展示一次，数据库仅保存凭证摘要。

样例环境位于独立项目 `../sample-provider/`，安装和启动见其 README。主体只接收接口数据，没有数据来源切换。

`npm run dev` / `npm run start` 同时启动本地备料调度，每分钟检查北京时间 20:00 的明日建议，并在闭店后完成日总结。调度不依赖打开浏览器；电脑关机期间停止，恢复后补生成并标明实际生成时间。`FORECAST_JOB_TOKEN` 自动保存在忽略提交的 `.env`。

首次建立数据库时，先 `npm run build`，再通过本地 Wrangler 依次执行 `drizzle/*.sql`。现有旧版数据库只需新增迁移 `0003_massive_robin_chapel.sql`，不要重复执行已应用迁移：

```sh
npx wrangler d1 execute DB --local --persist-to .wrangler/state --config dist/server/wrangler.json --file drizzle/0003_massive_robin_chapel.sql
```

## 统计与每日建议

管理端显示余量、最近五分钟消耗速度和最近三十分钟趋势，可展开查看同菜的多个碗。离线、拿碗和待确认变化不当作完整消耗。日总结区分秤测得的上台补充量和人工记录的厨房总备料量。

取用量来自稳定重量下降，不代表最终吃下的量；放置过久、当日剩余和其他报损需要人工记录。标准满量不会随补菜改变。单次取用可能包含多件食品，首版不推算件数。

明日备料采用按菜训练的重量模型，近期样本权重每七天减半，至少 21 个有效完整日才提供数值。默认余量 10% 可调整，修改或试供量需填写理由。确认计划不限制当天追加。

## 数据接入

联网秤通过设备上传接口提交毛重；历史系统通过版本 1 的历史接口提交克单位 JSON。主体不读取 CSV、模拟器或隐藏评估文件。样例环境负责把自身样例转换成统一协议。详见 [接口契约](docs/INTEGRATION.md) 与 [重量模型](docs/PREFERENCES.md)。

```sh
npm test

npx tsc --noEmit
npm run lint
npm run build
```

接口测试应在独立的测试实例和数据库上运行，写入验证秤并在结束时停用测试配置；历史测试会导入数据和更新凭证。使用 `SCALE_BASE_URL` 和 `LOCAL_URL` 指定该实例地址。旧视觉识别、收银、采购成本、经营分析和补菜任务的页面、接口及计算代码均已移除；旧业务表保留为历史，新系统不读取它们。这描述当前实现状态；新的 Agent 使用上述只读工具链路，不恢复旧页面或旧数据模型。

本版只在本地运行，尚未接真实秤芯片。硬件确定后由主设备适配 HTTP 协议，不进行线上部署。

智能分析当前采用周卡片入口 → 整周／每日图形画像 → 自动 AI 解读 → 单一菜品明细表。具体交互与缓存规则见 [可视化客群画像](docs/WEEKLY-PORTRAITS.md)。

新增与周卡片并列的“整体用户画像”：基于全部有效历史的日均取用与星期收缩估计，样本不足21天标为学习中；详见 [整体画像模型](docs/OVERALL-PORTRAIT.md)。

当前页面以“当前客群画像”为默认主视图，历史周／日画像退为次级入口。模型采用28天半衰期与星期先验，仅当当天覆盖、供应和设备新鲜度满足条件时加入当天修正；界面明确标注数据状态。详见当前画像模型说明。

## 菜品限时更换与供应反馈

时限更换融入原有实时、每日总结、智能分析三个栏目；旧地址 `/admin?view=freshness` 转到实时页。规则位于设备与菜品设置，按碗位登记批次，厨房屏幕以紧凑提醒条显示待处理事项。撤下后原子保存报损与供应反馈，提供分时段减量/试停供建议，接入备料页面和智能分析工具。补菜不会重置计时；建议须由管理者确认执行。规则、接口与使用说明见 [时限管理](docs/FRESHNESS.md)。

### 每日客群画像档案与按需解读

实时数学模型保持可查看，但所有 AI 解读均需点击生成，进入页面、切换日期或刷新数据不会自动调用模型。根据当前使用范围，仅展示2026年10月1日至4日的数值档案；它们为事后补算，保存实际生成时间与模拟来源，不能视为当日实时生成的预测。页面的“四天客群画像概览”基于这四天统计生成一次并持久保存在 `intelligence_reports`，再次查看或重复提交直接读取已存结果。

每日画像保存在 `portrait_archives`，模型不覆盖；未生成的每日 AI 解读需点击“生成这一天的解读”，成功后也固定保存。后台自动归档、自动 AI 分析与自动重试已暂停，调度端点返回跳过状态，不消耗模型 Token。已有其他日期档案保留在数据库中，本次不删除。此前每日归档调度的说明已由以上按需策略替代。


## 三维餐厅演示接入

同级 `../新建文件夹` 为三维演示前端。它通过 `GET /api/restaurant/state` 与本项目整合；该只读接口与厨房端 `/api/scales/state` 共用 `lib/scales/current.ts`，读取同一批已导入的观测数据。当前为统一数据集回放，数据时间与响应时间分别保留，缺测不使用隐藏真值补齐。

启动本项目后，在演示目录运行 `npm run build` 和 `npm run preview -- --port 4173`。演示的 Vite 代理把 `/api/restaurant` 转发到 5173；部署时需配置等价反向代理。42碗依 `position` 和菜品身份对应模型，余量以克提供，演示按比例分档展示。无客流观测时不生成顾客数。

### 每日可视化面板（当前策略）

智能分析首页现为每天一份的可视化客群面板，替代实时全历史重算与长报告。北京时间每天首次后台检查或打开页面时生成，存入 `intelligence_reports` 的 `daily-panel` 命名空间，按数据集与日期隔离。日期取实际北京时间；模拟历史晚于当前时间的部分不参与。面积、重量占比、样本数来自确定性模型，AI 只生成一句画像标题和逐菜悬停提示。一次生成固定当天数值，刷新只读取存档，不重新计算或重复调用模型。并发请求共用生成记录；AI 失败后保留数值面板，当日不自动重试。此前“四天概览／后台暂停”的策略不再用于此主面板，历史周日解读仍是手动生成。后台随本地服务运行，停机期间不回填旧日 AI；过去已有的每日面板通过日期选择查看。

每日可视化面板下方提供“取用倾向趋势”：从同一数据集的每日存档读取近7／28天各菜估计占比，与树图菜品选择联动；不重算模型、不调用AI。同模型参数与同参与菜品才比较，缺日保留断点，少于两个可比日期不判趋势。文字方向仅表示区间首尾变化，并非预测或统计显著性结论。

趋势现支持查看时即时补算：每次打开或切换7／28天范围，读取一次现有日历史，优先使用已保存画像，其余日期按当日截止时间重建模型估计。不写回每日档案，不使用之后日期的数据，不恢复历史实时修正，也不调用AI。图中空心点为历史补算、实心点为当天保存；样本不足及分母不一致仍不比较。


## 独立十分钟午餐演示（当前演示配置）

游戏与专用厨房页面现改用独立的 `data/lunch-demo` 仿真数据：2026-10-04 12:00–12:10，原速循环，42碗逐秒余量和顾客进出。通过 `/api/demo/lunch/state`、`/api/demo/lunch/control` 同步播放；厨房地址 `/demo/lunch/kitchen`。普通厨房和经营历史保持原数据源。详见 [午餐仿真说明](data/lunch-demo/README.md)。

趋势文字判断现由 DeepSeek 根据整段可比序列生成短标题和一句解释，图形和首尾百分点差仍为统计结果。服务端按菜品、区间、数据来源、模型口径和实际数值的内容哈希持久缓存；同数据跨刷新复用。悬停只查看提示，点击菜品或切换区间才触发分析（带防抖），失败不会自动重试，可手动重试。AI 未连接或数据不足时不以规则文案冒充 AI 判断。
