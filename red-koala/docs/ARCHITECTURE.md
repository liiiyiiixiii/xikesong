# 两层架构与分析设计

更新日期：2026-10-03。本文件定义项目方向及后续建设边界。智能分析首版现已实现，使用方法见 [智能分析说明](INTELLIGENCE.md)；其余目标以各项状态为准。

## 1. 定位与当前状态

红考拉是面向餐饮门店的数据处理与智能经营分析系统，默认先服务当前单店。厨房人员通过现有工作台掌握现场供菜，管理者通过统计、预测和Agent 分析了解整体及分时段客群的取用倾向，调整菜品供应，并逐步研究经营效果。

“客群画像”首阶段指按整体、日期和时段描述的群体取用行为特征，不涉及个人识别，也不推断年龄、身份等顾客属性。

| 能力 | 状态 | 当前边界 |
| --- | --- | --- |
| 设备毛重接入、校验去重、重量事件整理 | 已实现 | 依赖设备配置与稳定读数；真实硬件仍待联调 |
| 实时状态、分钟汇总、日统计及质量信息 | 已实现 | 存在观测覆盖、空盘和待确认变化等信息；已提供受限的 Agent 日统计与分时段只读查询工具 |
| 菜品取用趋势、明日备料预测、人工确认与执行记录 | 已实现 | 按重量建模，现有 `Profile` 是菜品趋势；不含人数和成本输入 |
| LLM Agent、整体趋势与分时段观测分析 | 首版已实现，真实模型待配置联调 | 提供四项只读工具、日期范围、结果与证据展示、报告导出；完整客群分层与更复杂管理洞察仍待建设 |
| 客流、排列历史、收入、成本及经营因素分析 | 依赖外部接入，并待建设 | 目前的接口不提供这些完整数据，不能使用旧表或模拟器隐藏信息代替 |
| 排列及供应量对照实验、经营效果评估 | 待建设 | 需实验执行记录和足够的结果数据，不能从观察相关性直接推断因果 |

## 2. 两层职责与数据流

外部系统 → 数据处理与统计层 → 可查询事实、指标及预测工具 → LLM Agent 智能分析层 → 管理者决策。样例环境也只能通过公开接口进入数据处理层。

### 第一层：数据处理与统计

接收外部数据，负责校验、去重、单位统一、事件整理、统计汇总与质量标记。已有的称重引擎区分取用、补充、报损、保留和测量修正；断线、拿碗及待确认变化不能当作完整取用。统计数值由程序计算，未知值不能作为零处理。

目标是提供按菜品、日期和时段查询的可靠事实，并让每个指标可追溯到数据来源、统计口径、覆盖范围及质量状态。目前已有实时和每日业务接口、内部分钟记录；首版已提供受限的日统计、指定整点时段汇总和证据核对；任意维度查询、复杂跨时段比较及长期证据存档仍待建设。

现有保留策略为原始采样 24 小时、分钟汇总 90 天、日统计和备料记录长期保存。追溯应明确使用原始采样还是汇总记录，不能承诺任意历史时点均可恢复原始数据。长期时段分析需要在后续建设中落实相应汇总与保存能力，当前设计不更改保留策略。

历史导入 v1 只有菜品目录、营业日和菜品日记录，不能还原日内取用过程。未来时段分析需使用有效的分钟或事件数据，或另行接入时段记录；时段起止需随分析结果明确展示，默认采用门店北京时间。

现有重量模型计算明日全天需求及参考范围，已作为 Agent 的只读试算工具。数值计算、预测与数据质量判断保留在工具中；模型输入、样本门槛与时间截断规则见 [重量模型说明](PREFERENCES.md)。

### 第二层：LLM Agent 智能分析

首版 Agent 按以下流程处理经营问题：

1. 理解问题，确定菜品、日期或时段、比较对象与目标指标；关键信息不明确时询问，无法确定时不擅自作结论。
2. 调用查询工具，获取事实、口径、覆盖情况、供应状态及缺失信息；先判断数据能否回答问题。
3. 调用统计或预测工具，完成排名、趋势、分组比较或备料预测。使用工具返回的数值，不用自然语言生成代替计算。
4. 核验样本、时间范围和供应条件，检查是否把缺菜误判为低偏好、把日预测误用为时段预测、把相关性误写为因果。
5. 输出有证据的结论与建议，明确需补充的数据或下一步验证方法；查询失败、模型不可用或样本不足时说明限制，不伪造结果。

工具能力按查询事实、统计比较和需求预测划分；首版工具名称、接口范围及默认 DeepSeek 配置见 [智能分析说明](INTELLIGENCE.md)，后续外部数据协议仍待确认。Agent 的分析不自动执行供应调整，建议由管理者确认后进入业务流程。

每份分析结果至少包含：问题与分析范围、观测事实、模型估计（如有）、结论及依据、数据缺口与限制、建议及待验证假设。记录使用的数据截止时间、指标口径和工具结果依据，让管理者能够核对。管理层重点查看趋势、异常、主要影响因素及需要采取的行动。

## 3. 分阶段能力与数据依赖

### 第一阶段：整体与时段客群

分析菜品取用量、重量占比、时段变化、供应不足和报损，结合现有明日预测提出备料建议。比较菜品时说明不同菜品单次取用重量、供应时长和缺菜可能影响排名；重量占比是取用结构，不能直接称为喜爱程度评分。

现有设备记录及有效分钟汇总可为时段分析提供基础，日历史只支持日级趋势。客流未接入时不计算人均取用、选择率或顾客覆盖率；缺少顾客与取菜关联时不声称识别出独立偏好群体。样本不足、未上市、缺菜或观测不完整时显示限制，不自动下架。

### 第二阶段：经营因素

按实际接入情况补充以下数据能力，不在本次固定外部报文：

| 数据能力 | 支持的问题 | 缺失时的限制 |
| --- | --- | --- |
| 同时段客流与统计口径 | 区分客流变化和取用强度变化 | 只能比较总量，不能计算人均或归因于客群偏好 |
| 排列及变更历史、菜品可接触机会 | 研究顺序、相邻组合与取用的关系 | 当前 `position` 只是固定排列顺序配置，不是历史或曝光记录，不能单独证明排列效果 |
| 供应可用时长、空盘和补菜情况 | 识别供应约束对取用的影响 | 当前空盘和观测覆盖只能提供部分证据，不能把全部低取用解释为低需求 |
| 对齐期间的收入、食材成本和报损成本 | 研究取用结构与经营结果的关系 | 重量排名不代表收入或利润贡献；成本收入覆盖不足不输出完整利润结论 |

分析需考虑时段、客流、供应、促销等同时变化的因素。观察数据支持关联描述及实验假设，不能单凭排列前后的变化证明利润提升。

### 第三阶段：实验与复杂分析

对排列或供应量调整设计对照实验，事先确定比较方案、观察周期和结果指标，记录实际执行、偏离情况及供应条件。具备收入和成本数据后才评估相应经营指标；利润口径应声明是否包含人工、租金、能源等费用。

根据实验设计和证据强度判断调整效果，无法排除客流、时段等因素时保留为待验证假设。Agent 可建议实验和解释结果，不能将未执行方案或模拟效果写成真实门店收益。

## 4. 接口、兼容与样例边界

文档规划阶段已结束；智能分析首版新增管理端入口和 `/api/intelligence`，不改变既有业务 API、数据库类型和历史接口版本。当前协议仍以 [接入说明](INTEGRATION.md) 为准：`/api/scales/ingest` 接收毛重，`/api/preferences/import` 接收 v1 克单位 JSON；预测导出可以使用 CSV，历史导入不接受 CSV。现有备料模型、人工确认和厨房流程继续保留。

主体与 `sample-provider` 独立运行，运行时仅通过 HTTP 供数。模拟器内部的顾客偏好、用餐会话及隐藏需求不作为主体已知事实；模拟经过流水也不等于主体已接入的排列曝光数据。隐藏信息仅可在主体外用于模拟验证，并明确标注，不能据此宣称真实预测或经营效果。

旧业务表继续保留为历史，不因规划新的 Agent 而恢复读取。此前移除大模型及经营分析描述的是代码状态，新的两层定位是后续建设方向。

## 5. 三个验收场景

以下用于检查设计是否明确证据和结论边界。首版通过工具链路测试不等于真实 DeepSeek 已联调成功；真实模型仍需配置密钥后验证。

| 问题 | 可用证据 | 缺失或待建设 | 允许得出的结论 |
| --- | --- | --- | --- |
| 哪些菜更受欢迎？ | 菜品日取用量、重量占比、近期趋势、供应和质量状态 | 选择人数、接触机会、反馈 | 描述在指定期间和供应条件下的高取用菜及偏好线索，不将重量排名等同喜爱程度 |
| 晚餐时段应增加哪些供应？ | 有效分钟或事件记录、空盘和补充信息；已有全天预测可作背景 | 足够的可比时段样本与完整供应覆盖；客流尚未接入 | 有时段证据时提出试供建议并人工确认；只有日历史时明确无法判断晚餐增量，不按比例臆造时段需求 |
| 调整排列是否提高利润？ | 当前位置配置与取用记录可作基础观察 | 排列变更与接触历史、可比客流及供应、收入成本、对照实验 | 提出相关性问题、需采集的数据和实验假设；现阶段不声称排列导致利润提高 |

文档验收需核对以上状态与现有代码、检查文档链接及接口描述一致性。代码验证方法见智能分析说明；此次开发不迁移数据库或部署线上。
